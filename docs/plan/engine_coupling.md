# 引擎耦合面与 review 影响评估

> 用途：`umaai-next` 计划做一轮机制 review（部分机制会改）。本文盘点 onsen 对引擎的实际依赖面、
> 把「改动 → 冲击」分成可判定的等级、给出 review 期间的缓冲措施与逐主题速查表。
> 维护时机：引擎每次机制变更后与 A4/A5/A6 落地后各刷新一次。

***

## 1. 当前耦合面（2026-10-19 实测）

### 1.1 依赖与规模

| 项 | 值 |
|---|---|
| 依赖 crate | 稳定面 `umaai-core` / `umasim` / `umaai`；样例面 `umaai-cli`（仅 bin 与测试） |
| 契约实现 | 33 个方法（`Game` 22 必备 + 默认覆盖 + `TrainingValueSource` / `ActionEnum` / `Deref`） |
| 直接触及引擎的代码 | `src/lib.rs` 595 行中的 **47 行（约 8%）** |
| 剧本数据 | 自持（`OnsenData`，不依赖引擎数据根结构） |

耦合面小是好信号：review 的多数改动只会打在少量行上；**危险的不是"改得多"，而是"改了不报错"**（见 §2）。

### 1.2 直接访问的底座成员（`self.base.*`）

| 成员 | 次数 | 用途 |
|---|---:|---|
| `uma` | 6 | 五维 / 体力 / 干劲 / flags / 比赛回合判定 |
| `turn` | 4 | 回合窗口、阶段流转 |
| `friend` | 3 | 友人解锁状态、出行次数 |
| `train_level_count` | 2 | 设施等级 |
| `master` | 2 | 策略流派生基点 |
| `distribution` | 2 | 人头分布读写 |
| `take/put/reset/init_rule_streams` | 4 | 三条随机轴的取出-放回与回合边界派生 |
| `race_grade` / `push_race_event` | 2 | 自选比赛可用性与事件构造 |
| `is_xiahesu` / `apply_event` / `deck` / `absent_rate_drop` | 4 | 合宿、事件结算、卡组、不在率 |

经 `Deref` 隐式触达（不写 `self.base` 也能改到底座）：`deck`（4 处）、`unresolved_events`（1 处）。
**这两处是最脆的**：引擎改字段名会编译报错（可发现），但改语义不会报错。

### 1.3 引擎数据表与宿主注入

- 引擎表：`consts`（五维上限兜底、事件概率、休息权重等）、`events`（系统事件 / 友人事件）、`umaDB`（生涯赛与免费赛）。
- 宿主：`Config`（`sim.*`、`inherit()`、`race_grades()`）、`Runner`、`Data::init`。
- 剧本侧：`OnsenData`（源泉 / 挖掘 / 事件表 / 训练表 / 上限基值），根目录由宿主注入。

## 2. 影响分级（review 时按此判）

| 级 | 含义 | 典型例子 | 探测手段 |
|---|---|---|---|
| **A 编译期破坏** | 签名 / 字段 / 变体改名或删除 | 钩子改名、`Person` 加必备方法 | path 依赖下立即可见，改动可控 |
| **B 静默数值位移** | 公式 / 查表 / 取整 / 随机消耗次序变 | 训练值公式、挖掘查表、事件概率 | 编译通过、终局变；**必须靠剧本仓自持基线** |
| **C 语义变更** | 同名同签名、含义变 | 等级表口径、默认实现公式、结算顺序、行为门控 | 只能靠 review 逐条对照 §1 清单 |
| **D 样例面破损** | `umaai-cli` 呈现件变动 | `PrintFrontend` / `render` 改名 | 只影响 bin 与测试，改动便宜 |
| **E 可复现性口径变更** | 随机分层 / 种子派生变 | 每回合派生规则、策略流归属 | 旧种子与全部基线失效（"可比性"而非"能否跑"） |

> 现状：A 级已被 `cargo check` 兜住；**B 级目前无自动化探测**（只有"跑满 + 同种子可复现"两条守门）。
> → 强烈建议 A4 落地时同步建立剧本仓数值基线（见 §4.2）。

## 3. review 主题 → onsen 影响速查表

| 引擎 review 主题 | onsen 触及点 | 级别 | 处置建议 |
|---|---|---|---|
| 训练值公式 / 上下层 | `calc_training_value` 覆写（A4 计划的首个真实消费者） | B / 高 | 公式或取整变要同步改剧本并重录基线 |
| 事件与羁绊 / 红点 | `default_after_train`、`apply_event`、`add_friendship`，红点由剧本覆写 `distribute_hint` | C / 中 | 口径变化（羁绊基值、爱娇出口、事件归属）直接改剧本数值 |
| 比赛结算 / 等级表 | `push_race_event`、`race_grade` | C / 中 | 已按「0=无比赛、1=G1…4=OP」实现；再动需两仓同步 |
| 人头与分布 | `init_persons`、`distribute_all`、`deyilv`、分身（负数占位） | B / 中 | 秘汤分身依赖「≤5 人 / 同训练位不重复 / 每位至多一个友人」约束 |
| 随机轴与种子派生 | `init/reset/take/put_rule_streams`、`StrategyRng` 派生 | **E / 高** | 改一次全部旧种子失效；剧本只走这套入口，绝不自己摸 OS 随机 |
| 阶段与 `StageId` | 剧本自持枚举 → 投影 0..4 | C / 低 | 引擎只透传；改号＝旧种子失效，尽量不动 |
| 数据与配置 | `OnsenData` 自持；`Config` 覆盖层泛型解析 | A / 低 | helper 变形只影响剧本配置段 |
| 搜索与 leaf（M2） | `FlatSearchGame`（**尚未实现**） | — / 低 | review 定稿前不要接；A10 / A11 仍在待定 |
| 呈现 / Frontend | bin 与测试用 `PrintFrontend` / `render` | D / 低 | 样例面不承诺稳定；必要时自实现 `Frontend` |
| 引擎数据表结构 | `consts` / `events` / `umaDB` | B / 中 | 表结构变会**静默**改剧本数值（事件概率、上限兜底） |

## 4. 缓冲措施（降低 review 冲击）

### 4.1 重构优先：跟随引擎，只记位移
定位明确——**温泉剧本是用来打磨基础库的，功能为副**：引擎该改就改，onsen 跟随并重录基线，不为兼容旧数值做妥协。
唯一要保留的纪律是**位移记录**：每次引擎改动后记录"哪些量变了、变了多少、归因是哪条机制"，
因为 B 级位移本身不报错，没有记录就无法区分「预期中的重构位移」与「意外的破坏」。

### 4.2 建立剧本仓数值基线（A4 起，定位＝变更探测器）
同种子终局五维 / PT / 评分 + 关键中间量（挖掘完成回合、券数、超回复次数、旅馆档）。
它是**探测器不是契约**：重构后数值该变就变，跑一次生成新基线即可；价值在于"变了"这件事一定被看见、
且能逐项对上 §3 速查表的归因。记录格式建议一基线一文件 + 一句位移说明（场景 / 引擎提交 / 变化清单）。

### 4.3 引擎交互收口（详见单独设计）
当前 47 行散在 `lib.rs`；A4–A6 会显著增加。做法与能力清单见
[`engine_adapter.md`](engine_adapter.md)：把「和引擎对话」的代码收进 `src/adapter.rs`，
机制代码只认剧本语言；**时点在 A4 之前**（早做便宜，晚做要返工改写新增机制代码）。

### 4.4 不提前依赖未定项
A12（`apply_event` 的 scale / vital_scale）、A13（hint 次数 / 等级复用件）、A10 / A11（搜索与 leaf）
在引擎定稿前由剧本侧自持实现；定稿后若要切换，作为一次独立改动评估。

### 4.5 契约面冒烟测试
`tests/` 增加一条覆盖 22 个必备方法调用路径的契约冒烟：引擎改签名时第一时间定位到剧本侧受影响点。

### 4.6 review 结论回写
引擎 review 若改变通用件形态（H1 / H2 / H4 / H5），把结论回写
[`m1_plan.md`](m1_plan.md) §4 与 [`library_candidates.md`](library_candidates.md) §5，保持两仓文档一致。

***

## 5. 时机建议

- **重构优先**：引擎 review 不必等 onsen——onsen 是打磨基础库的手段，机制随重构调整、基线随重构重录属预期。
- 建议的顺序：**先立适配层（§4.3）→ 再做引擎 review**。这样 review 的每一处改动都能立刻映射到适配层的少量方法上，
  并用剧本仓基线当场量出位移；反过来，适配层的方法清单（＝引擎稳定面的真实使用面）也是 review 的输入。
- 若 review 必须先于适配层：直接改即可，只是改动面会随机制代码增长而扩大（A4 后预计破百行）。

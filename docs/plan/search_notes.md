# 源泉选择的搜索难点与优化方向（M2 前置分析）

> 背景：拉面的「地区选择」**无依赖**，每年独立，搜索可分解、方差小；温泉的「源泉选择」是
> **带截止期的承诺式排程**，旧仓 MCTS 在这上面计算量表现不佳。本文记录问题结构、旧失败原因、
> 新引擎新增的杠杆、候选优化方向，以及「现在是否该拍搜索架构」的结论。

***

## 1. 两者结构差异

| | 拉面 地区选择 | 温泉 源泉选择 |
|---|---|---|
| 决策点 | 每年一次，**相互独立** | 初始 + 每次挖完 + 强制再选择（回合 24 / 48 / 65），约 4–8 次，**前后耦合** |
| 选择后果 | 只影响当年收益 | ①决定「能否在下次强制再选择前挖完」②决定效果生效时点 ③决定这段时间的挖掘力成长路径 |
| 收益兑现 | 选定即生效 | **只有挖完才生效**；未挖完只按每 30 进度给属性奖励，进度按泉保留但需回到该泉继续 |
| 反馈 | 短期、可即时评估 | 长程、稀疏（完成才兑现），且完成时点本身是随机的 |
| 与训练的关系 | 弱 | **闭环**：挖掘力吃五维档位与装备，五维靠训练，训练受策略与体力影响；选泉又改变训练收益 |

一句话：拉面是「每年一个小决策」，温泉是「对一个 10–25 回合的承诺下注，且截止期会被强制再选择打断」。

***

## 2. 旧仓 MCTS 表现差的机制原因

1. **稀疏长程奖励**：温泉效果只在 `掘削完了` 兑现，而完成时点取决于随机训练成败与人头分布；
   以 78 回合终局分作 rollout 回报时，噪声远大于「选泉 A vs B」的真实差。
2. **闭环耦合**：选泉 → 训练内容 → 五维 → 挖掘力 → 完成时点 → 下一轮选泉，任一处随机都会放大。
3. **CRN 对齐失效**：旧温泉是旧仓里**唯一未做三流改造**的剧本（规则随机与决策抽签共用一条流），
   靠外挂「按 (rollout 种子, 回合, 阶段) 重播种」对齐；而**选泉/装备升级在 `Begin` 内执行、没有独立阶段键**，
   不受重播种保护——同一批 rollout 的随机性对不齐，配对收益拿不到。
4. **预算用错地方**：候选分支因子 3–6、决策点 4–8 个，但每个节点都跑完整局 rollout；
   周期内的大量决策（训练/休息/出行）其实高度同质，用搜索求解是浪费预算。

***

## 3. 新引擎带来的三个新杠杆（这是「是否有优化思路」的正面回答）

1. **按 `(master, turn)` 派生的规则流**：同一主种子下，两支只在选泉上不同的分支，**规则随机逐位一致**。
   → 可以做**配对差分**（paired difference）：比较的不再是两个独立均值，而是逐样本的差，
   同方差下所需样本量降一个量级。这正是旧仓想用外挂重播种达到、却因 Dig 在 Begin 内而没达到的效果。
2. **`fork_for_rollout` 是唯一分支入口**（克隆 + 注入 rollout 种子 + 重置自持流）：
   分支语义被引擎钉死，配对与可复现性由结构保证，不靠纪律。
3. **`StageId` 显式赋号**：搜索层可以按「剧本决策点」定义分段键——旧仓的 `stage_seed` 是**重播种**，
   新方案是**定义边界**（option 键），语义更干净。

***

## 4. 候选优化方向（按杠杆排序，M2 选型用）

| # | 方向 | 做法 | 收益 | 归属 |
|---|---|---|---|---|
| P1 | **配对 CRN** | 任何「选泉 A vs B」比较都在同一 master、同一分支点配对；报告配对均值 / SE / t | 方差降一个量级，结论可信 | 引擎搜索层已有基础，剧本仓加记录 |
| P2 | **Option 分解（半马尔可夫）** | 搜索单位＝「选泉周期」（本次选泉 → 下次选泉/强制再选择）；周期内用固定基策推进；周期边界用廉价估值 | 复杂度从 `候选^决策点 × 78 回合` 降到 `候选 × 周期长度` | 引擎需分段搜索 seam（A11） |
| P3 | **可行性 / 支配剪枝** | 用当前挖掘力与动作分布的确定性估计算「完成所需动作数」，与到下次强制再选择的回合数比较；不可完成的分支要么剪掉，要么只按部分进度收益估值 | 直接砍掉大半无意义分支 | **剧本仓**（规则知识；memo 攻略本身就是这类规则） |
| P4 | **预算再分配** | 只在选泉 / 升级 / 入浴等稀疏关键点开搜索，其余用最小手写策略 | 与旧仓 `mcts_selected_onsen` 方向相反（旧是选泉用手写、其余搜索） | 剧本仓 + 引擎接口 |
| P5 | **截断搜索 + 手写 leaf 估值** | 旧温泉是唯一 `SUPPORTS_TRUNCATED_LEAF = true` 的剧本；新引擎的 leaf 估值器属 NN 延后项，可先给一个不依赖 NN 的手写估值（五维 + 已生效效果 + 未完成进度 + 剩余券/回合） | 省掉大段 rollout | 引擎（A10）+ 剧本估值 |
| P6 | **并行与树复用** | rollout 相互独立（每回合派生）→ 直接吃 `parallel` 特性；同根候选共享克隆前缀 | 硬件层面的线性收益 | 引擎已具备 |

***

## 5. 非搜索的替代路线（必须与之对照）

| # | 路线 | 说明 |
|---|---|---|
| R1 | **规则化排程策略**（顺序表强化版） | 按「构建需求 × 截止回合 × 可完成性 × 效果价值」排序选泉；旧仓就是固定顺序表 + 秘汤豁免，说明「表 + 少量例外」已能跑 |
| R2 | **规则为主 + 边界情形搜索** | 默认按表；仅当边界情形（差一点挖完 / 效果与构建冲突 / 券数与超回复冲突）才开搜索 |
| R3 | **完全搜索** | M2 目标形态，但需先用 P1–P5 把成本压下来再评估 |

***

## 6. 结论：现在不拍搜索架构，M1 只做「测量与记录」

M1 不做搜索，但**要为 M2 攒三个数**：

1. **影响半径**：同根两分支只改一次选泉，终局分差 Δscore 的分布 —— 直接用引擎已有的
   `umaai-tools compare`（同根两分支推进对照）就能测，不需要搜索。
2. **可完成率**：每次选泉的候选里，各候选在「下次强制再选择」前真正挖完的比例（按当前挖掘力与剩余回合）。
3. **方差**：配对差分的 SE —— 决定 M2 需要多少 rollout、是否值得做 option 分解。

M1 的实现相应地要**顺手记录**：每次选泉的候选集、选中项、当时的回合 / 挖掘力 / 剩余量 / 券数，
以及该泉最终是否挖完、在第几回合挖完。这份记录本身就是 P3 剪枝规则的训练数据。

**M2 的推荐起点**：P1 + P2 + P4（配对 + option 分解 + 预算再分配）先做最小可用搜索，
P3 / P5 按测量结果加；R1 / R2 作为对照组保留（也是线上兜底）。
